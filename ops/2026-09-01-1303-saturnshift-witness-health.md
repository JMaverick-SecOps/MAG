# SaturnShift and Base witness production check

- Primary learning target: reproducible testing.
- Baseline: direct Base-USDC intake reported ready, but the two configured witness identities and current provider-side SaturnShift access needed fresh verification.
- Observation: the authenticated read-only `/admin/payment-rpc-health` diagnostic returned `ready=true` for both Alchemy and OnFinality. Each independently completed finalized-block, historical-transaction and historical-receipt reads. The diagnostic explicitly reported `real_payment=false`.
- SaturnShift checkout observation: the public checkout loader creates a payment intent and redirects to the hosted checkout URL. It exposes no signed browser-return artifact, webhook secret or final-settlement proof that MAG could safely use instead of the provider webhook.
- PSP access observation: SaturnShift's public dashboard bundle includes a PSP Developers route at `/psp/developers` with account-specific credentials, webhook creation/rotation, delivery history and signed-test actions. The current authenticated merchant role is redirected from that exact route to `/dashboard`; `/admin/settings/developers` exposes only the public checkout integration.
- Provider conversation observation: the SaturnShift assistant response supplied generic webhook setup steps and asked for platform/events. It did not grant PSP access, register the endpoint, issue a signing secret or produce a signed test receipt.
- Falsifiable hypothesis: if both Base witnesses are configured and currently capable, the owner-only production diagnostic will report two distinct operators ready for finalized and historical reads. It did. If the merchant account has PSP webhook authority, the exact PSP Developers route will render its credential/webhook controls. It did not.
- Outcome: `improved` for verified witness readiness and provider-boundary diagnosis; `no_change` for SaturnShift activation. Direct Base-USDC payment verification is operational. SaturnShift remains fail-closed until the provider grants PSP Developer access, the account-specific secret is installed through an encrypted binding, and a provider-generated signed no-charge test succeeds. No charge, transfer, secret disclosure or entitlement change occurred.
